本章的主线是：**上下文不只是提示词，而是 Agent 在当前回合能看到、能复用、也必须控制成本的信息集合。** 章节从 KV Cache、提示工程、Agent Skills 到上下文压缩，讨论如何在“保留必要信息”和“限制 token、延迟与溢出风险”之间取得平衡。

这份笔记聚焦本次实际接触的 `context-compression` 实验，并补充第 2 章的整体位置。截图中的错误与数值均按原样记录；它们反映本次环境和服务状态，不等同于通用性能结论。

## 1. 本章的核心认识

### 1.1 为什么上下文会成为 Agent 的瓶颈

一个会检索、浏览和调用工具的 Agent，会持续把以下内容加入对话：用户目标、系统指令、工具定义、搜索结果、网页正文、历史推理与工具轨迹。上下文越长，通常会带来四类问题：

| 维度 | 问题 |
| --- | --- |
| 成本 | 输入 token 增加，推理费用随之上升 |
| 延迟 | 每一轮都要处理更长的历史，响应变慢 |
| 可靠性 | 可能超过模型或应用设定的上下文预算 |
| 相关性 | 旧信息挤占注意力，模型更难聚焦当前任务 |

因此，压缩的目标不是“把文本变短”这么简单，而是：**在固定预算内尽量保留完成当前任务所需的证据、约束和最近状态。**

### 1.2 上下文工程的四个层次

1. **请求稳定性与 KV Cache**：把稳定的系统指令、工具定义和固定前缀尽量放在前面，避免无谓改动，从而提高前缀缓存复用的机会。
2. **提示工程**：用清晰的角色、约束、输入变量和输出格式，让模型知道当前回合最重要的信息。
3. **Agent Skills**：把可复用流程、规则和示例按需加载，而不是把所有知识一次塞入上下文。
4. **上下文压缩**：当工具轨迹与网页内容不断累积时，按策略摘要、筛选或滑动窗口处理历史。

### 1.3 一个实用判断

> 不应只问“压缩率有多高”，还要问“压缩后是否仍保留了回答当前问题所需的可验证事实”。

## 2. 实验 2-10：上下文压缩策略对比

### 2.1 实验目标与任务

实验使用“查询约 11 位 OpenAI 联合创始人的当前任职机构”作为压力任务。这个任务需要反复搜索与抓取网页，能够自然累积大量工具返回内容，因此适合观察不同压缩策略的 token 使用、溢出、耗时和任务完成情况。

实验会记录：成功状态、迭代次数、总 token、压缩比、上下文溢出次数、工具调用与最终答案长度。代码默认将演示预算设为 `128K`，即使所用模型的真实窗口更大，也能观察压缩和溢出的行为。

### 2.2 六种策略

| 策略 | 做法 | 适用场景与取舍 |
| --- | --- | --- |
| 无压缩 | 网页全文直接加入上下文 | 作为基线；信息最全，但最容易超预算 |
| 逐页摘要 | 每个页面分别摘要，再拼接 | 保留来源粒度；额外模型调用较多，跨页关系可能丢失 |
| 合并摘要 | 先合并内容，再做一次总摘要 | 整体视角更好；页面归因可能变弱，输入过大时摘要本身也可能受限 |
| 上下文感知摘要 | 围绕当前查询提炼结果 | 相关性与长度通常更平衡；需要额外一次模型调用 |
| 带引用的上下文感知摘要 | 在感知摘要中保留来源链接 | 便于追溯和后续问答；内容会略大 |
| 窗口化上下文 | 保留最新工具结果全文，压缩较早历史 | 适合长、多轮任务；可保留近期细节，但压缩时机需谨慎设置 |

### 2.3 官方真实运行对比（2026-07-18）

下表来自实验仓库 README 中的一次端到端真实运行：Kimi K3、真实 Serper 检索和网页抓取、`128K` 演示预算、最多 15 轮。单次绝对数值会变化，重点是理解不同策略的相对取舍。

| 策略 | 成功 | 迭代 | Token | 压缩比 | 溢出 | 耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 无压缩 | 否，165,227 token 时超出 128K | 5 | 166,043 | 102.1% | 1 | 107s |
| 逐页摘要 | 是 | 12 | 276,608 | 10.9% | 4 | 2,980s |
| 合并摘要 | 是 | 10 | 93,449 | 4.3% | 0 | 1,189s |
| 上下文感知摘要 | 是 | 7 | 40,157 | 3.0% | 0 | 967s |
| 带引用的感知摘要 | 是 | 10 | 222,992 | 4.1% | 3 | 1,235s |
| 窗口化上下文 | 是 | 7 | 174,601 | 102.4% | 4 | 867s |

我的解读：

- 无压缩的失败说明“模型窗口很大”不等于可以无限累积工具内容；系统仍应有明确的预算管理。
- 这一次运行中，上下文感知摘要以较少 token 完成任务，说明“围绕当前问题提取”比机械截短更有效。
- 窗口化策略的字符压缩比接近 100%，却完成得很快。这不是压缩失效，而是它优先保留了最新的完整内容，并只在达到阈值后处理较早历史。
- 带引用策略的价值主要在可追溯性；是否值得额外 token，要看任务是否需要审计、追问或引用来源。

## 3. 本次运行记录 A：长上下文与服务限流

### 截图观察

运行到第 6/15 轮时，Agent 抓取了 Greg Brockman 的 Wikipedia 页面，单页工具返回约 37,393 个字符；当前提示 token 为 47,257，总 token 为 48,425。随后 Moonshot 接口连续返回 HTTP `429 Too Many Requests`，日志显示组织级 RPM 上限为 3。重试后研究任务失败。

| 指标 | 截图值 |
| --- | ---: |
| 工具调用 | 12 |
| 上下文溢出 | 0 |
| 总 token | 48,425 |
| 输入 / 输出 token | 47,257 / 1,168 |
| 压缩比 | 140.4% |
| 节省字符数 | -1,802 |
| 失败原因 | HTTP 429：请求频率超限 |

### 关键结论

1. **这次失败不是上下文溢出。** 虽然实验主题涉及长上下文，但统计中的 `Context Overflows: 0`；直接原因是服务端速率限制。排障时必须区分“模型预算不足”和“外部服务不可用”。
2. **压缩并不保证每轮变短。** `140.4%` 压缩比和负的节省字符数表示本轮处理后的内容反而膨胀了。这可能发生在输入很短、摘要模板或补充说明相对较长时。
3. **应把限流纳入 Agent 工程。** 生产系统需要指数退避、并发与 RPM 控制、可恢复的断点、以及把“暂时不可检索”明确暴露给用户，而不是把它误判为模型推理失败。

## 4. 本次运行记录 B：动态感知上下文与证据质量

### 截图观察

运行在处理查询 `Pamela Vagata engineer Stripe current company 2025` 时，系统尝试根据当前问题生成“查询聚焦摘要”。Serper 搜索接口返回 HTTP `403`，随后日志明确提示搜索结果只是“未配置 API Key 时的占位／模拟数据”，无法从中提取真实信息。

但 Agent 没有把模拟数据当成事实：它输出了“来自既有知识，未验证且可能过时”的内容，说明 2025 年当前任职无法由本次结果确认，并建议在可用的搜索 API 下重新验证。该轮日志还显示一次压缩从 54 个字符扩展到约 1,518 个字符；第 9/15 轮累计 token 为 117,327。

### 关键结论

1. **动态感知压缩以任务相关性为优先级。** 它不是固定字数裁剪，而是围绕当前 query 决定哪些信息应进入下一轮上下文。
2. **“压缩”可能合理地扩写。** 当工具返回很短但信息质量不足时，系统补充风险说明、已知背景与验证建议，会让结果比原始输入更长；这比简短但误导的结论更好。
3. **上下文管理无法替代数据验证。** 检索服务 403 或返回 mock data 时，压缩算法只能整理已有信息，不能把缺失的证据变出来。
4. **需要在上下文中保存证据状态。** 建议把来源、抓取时间、是否真实检索、是否已验证等字段与摘要一起保留，避免后续回合把“未验证背景”误用为“已证实事实”。

## 5. 我的实现与排障清单

### 运行前

- 明确模型的真实上下文窗口与应用层预算，不把二者混为一谈。
- 配置可用的 LLM 和搜索 API Key，并用一次小查询确认返回的不是 mock data。
- 限制单页抓取长度、搜索结果数与最大迭代轮数，避免异常网页迅速吞掉预算。

### 运行中

- 每轮记录输入 token、输出 token、工具调用、压缩前后长度和摘要来源。
- 触发预算阈值时，优先保留：当前任务约束、最近工具结果、关键数字／实体、以及来源链接。
- 对 429 使用退避和限速；对 403、空结果或占位结果标记为“未验证”，不要自动补写成事实。

### 运行后

- 同时比较成功率、耗时、token、溢出次数和答案的证据完整性。
- 抽样检查压缩后的摘要是否仍包含关键约束、数值、否定条件和来源。
- 按任务类型选策略：短而独立的资料可用逐页摘要；多来源问答优先感知摘要或带引用摘要；长、多轮工具任务适合窗口化上下文。

## 本章小结

> 上下文工程的本质是信息预算管理：让 Agent 在有限窗口中看见最相关、最可信、最接近当前行动的信息。

本次实验尤其提醒我：**上下文溢出、API 限流和检索质量是三类不同问题。** 压缩策略可以缓解 token 预算压力，但不能解决限流，也不能替代可靠的数据来源与证据核验。
